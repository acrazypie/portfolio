WAYL

A self-hosted music log. Track what you listen to, keep your history on your own server, and share playlists with friends who run their own.

  • role solo · design + full-stack
  • stack Python · Flask · SQLite · vanilla JS · Docker
  • status v1 public since November 2026 · in active development
  • timeline started in late 2025, about a year of work
live site ↗ source ↗

01 // tl;dr

  • What: a personal music log that runs on your own server. Search any song, log what you play, build playlists, see your stats.
  • What I built: all of it, alone. A Flask API, a vanilla JS front end with no build step, a sync worker for Plex and Navidrome, a Docker setup and 90 tests in CI.
  • The interesting part: instances share playlists through read-only links. No accounts across servers, no central server.

02 // why I built it

I wanted to cut my expenses and be more deliberate about where my money goes. Paying every month to rent music I'd never own, while handing over my listening data, stopped making sense.

I'd rather own my music and support artists directly. But owning files means losing what streaming apps do well: history, stats, playlists, finding music through friends. WAYL is how I keep those without giving my data away.

03 // what it does

Log and search

Search any song through MusicBrainz and ListenBrainz, log what you play, save favourites, see your top songs and artists. No API keys, no song library to maintain.

Your own music server

Connect Plex or Navidrome: WAYL logs your plays automatically, imports your playlists and marks the songs you already own.

Stream in the browser

Play your own files through WAYL. Your server's address and login never reach the browser.

Share with friends

Send a link to a playlist or your profile. Friends running their own WAYL subscribe to it and see which songs they already have.

04 // how it fits together

Two containers from the same Docker image: the web app and a worker that keeps music servers in sync. All data lives in one SQLite file, in one volume.

Browser the single-page app, plain JS
Friend's WAYL reads your share links
Navidrome · scrobblers sends listens through the ListenBrainz-compatible API
WAYL · Flask REST API · share endpoints · audio proxy · sync worker
SQLite one file, Alembic migrations
MusicBrainz · ListenBrainz song metadata, free and keyless
Plex · Navidrome your library, plays and playlists

05 // key decisions

001

A personal log first, social second

context
Early versions had follows and a feed. But a self-hosted instance usually has one user, so a social graph inside it makes little sense.
options
Keep social at the core · drop it · make it optional.
choice
Social features are off by default and turn on with one setting (WAYL_SOCIAL=1). Core code never depends on them.
trade-off
Two configurations to test. The suite covers both: social tests are marked and get their own app instance.
002

Sharing without a central server

context
I still wanted friends to see each other's music, without running a server everyone depends on.
options
A central hub · full federation with accounts across instances · read-only links.
choice
Capability URLs: each share is a link with an unguessable token. Any WAYL can subscribe to it and re-checks it every 6 hours. Only song metadata crosses instances, never audio, emails or server addresses. The format is versioned and documented.
trade-off
No comments, likes or live updates, and your instance needs a reachable address (a domain or Tailscale). In exchange there is nothing to moderate and nothing I have to keep online for others.
003

Open music data instead of Spotify

context
A music log needs song data: titles, artists, albums, covers, credits.
options
Spotify · Deezer · iTunes · MusicBrainz and ListenBrainz.
choice
MusicBrainz and ListenBrainz: free, no API key, and the core data is public domain, so storing it is fine.
trade-off
MusicBrainz allows one request per second, so WAYL throttles itself and caches searches for 10 minutes. The alternatives were worse: Spotify has restricted its API, and Deezer's terms forbid storing their metadata.
004

Flask, SQLite and no build step

context
People self-hosting this, me included, want something that starts with one command and is easy to back up.
options
Postgres and a JS framework · Flask, SQLite and plain JavaScript.
choice
Flask, one SQLite file and plain JavaScript. docker compose up -d and it runs; a backup is one volume.
trade-off
SQLite doesn't like many writers at once. That's fine for a personal or family instance, which is what WAYL is for.

06 // challenges

Matching messy track names

Files on a server are called things like “Teardrop - 2006 Remaster” or “Artist feat. Someone”. To know which songs you own and log plays correctly, WAYL normalizes both sides (remaster tags, featured artists, punctuation) before comparing, or uses the MusicBrainz id when files are tagged. Listens that still don't match wait in Settings and are retried after a week.

Not letting a pasted link become an attack

Subscribing means your server fetches a URL someone gave you. On a public instance that could be abused to make WAYL request addresses on its own network. With ALLOW_PRIVATE_SERVER_URLS=0, WAYL resolves the host first and refuses any private, loopback or reserved address.

Keeping server logins secret

WAYL stores Plex and Navidrome logins so it can sync in the background. They're encrypted at rest, never returned by the API, and audio is proxied through WAYL so the browser never sees them. Navidrome only ever receives a salted hash of the password.

07 // testing

  • 90tests
  • 2Python versions in CI
  • 0network calls in tests

The suite runs with pytest on every push and pull request. It never touches the network: the music catalog is replaced with canned responses, and fake Plex, plex.tv and Navidrome servers stand in for the real ones.

It covers sign-in and password reset, the API, server sync, and both sides of sharing. This is a first public version, so the next real test is people running it on their own hardware.

08 // what's next

  • A mobile app, so you can stream your own music away from home.
  • Hardening v1 against real setups as more people self-host it.
  • A stable sharing protocol, so other tools can read WAYL links too.
